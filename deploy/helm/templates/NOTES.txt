2. Confirming the version each instance reports
-----------------------------------------------
The reported version is the CONFIG_VERSION env var, injected by config-service
canary distribution (ADR-0006). Compare it across replicas and against the
latest version the control plane holds — a mismatch that persists is what
ASConfigDrift alerts on (deploy/alerts/as-alerts.yaml).

  kubectl -n {{ include "as.namespace" . }} get pods -l app.kubernetes.io/part-of=3rdparty-as \
    -o custom-columns=POD:.metadata.name,USE_CASE:.metadata.labels.app\.kubernetes\.io/use-case,READY:.status.containerStatuses[0].ready

3. Triggering a rollback
------------------------
Two different things are called "rollback"; do not confuse them.

  a) Configuration rollback (ADR-0006): roll back the change order from the
     console / config-service — the previous config version is redistributed to
     the instances. This is what ASConfigRollbackTriggered alerts on, and it
     always needs a human to confirm afterwards.

  b) Image / manifest rollback: revert the Helm release and let the Deployment
     roll the Pods back. Draining applies on the way out (ADR-0009):

       helm -n {{ include "as.namespace" . }} history {{ .Release.Name }}
       helm -n {{ include "as.namespace" . }} rollback {{ .Release.Name }} <revision>
       kubectl -n {{ include "as.namespace" . }} rollout status deploy --selector app.kubernetes.io/part-of=3rdparty-as
