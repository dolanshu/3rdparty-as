work, Python SIP wire/policy seams, and a standalone native reSIProcate probe.

into this first build step. This handoff preserves the source and last native
build so the next machine can first try to reuse the libraries instead of
immediately rebuilding them.

The earlier assistant estimate of **9–14 engineering days** for the remaining
M2 work is withdrawn. It did not account for the absent product integration,
cross-machine build portability, or the unresolved M2/M7 adapter boundary. Do

### Build Baseline And Portability

The validated machine was Ubuntu 20.04.2 LTS, Linux x86_64/WSL2, GCC 9.4.0,
CMake 3.31.12. The probe CMake project requires CMake 3.21 or later. The shared
libraries depend on `libssl.so.1.1`, `libcrypto.so.1.1`, `libcares.so.2`, and
standard C/C++ runtime libraries. The source build used `libpopt-dev`,
`libc-ares-dev`, and system OpenSSL development files.

The prebuilt probe has an absolute RUNPATH into
`/tmp/as-resiprocate-m2-build-20261004`. Its CMake cache also contains absolute
author-machine source and repository paths. On a compatible Linux x86_64 host,
extracting to the original `/tmp` paths may allow direct probe reuse. First run
`ldd`; if any dependency is missing or has an incompatible ABI, rebuild. Do not
assume a newer distribution with OpenSSL 3 can load these OpenSSL 1.1
libraries. The archived probe CMake cache should not be reused from a different
checkout path.

To relink the probe against the bundled native libraries from a different
checkout path, run from the repository root after restoring the archives:

```sh
cmake -S "$PWD/testbed/simulators/resip-probe" \
  -B /tmp/as-resiprocate-m2-probe-rebuild-20261004 \
  -DRESIP_HOME=/tmp/as-resiprocate-m2-20261004 \
  -DRESIP_BUILD=/tmp/as-resiprocate-m2-build-20261004
cmake --build /tmp/as-resiprocate-m2-probe-rebuild-20261004 --parallel 4
```

If the native libraries cannot be reused, configure a fresh out-of-tree
reSIProcate build from the restored source. The flags below match the minimal
library selection used for the probe; CMake/compiler/system dependencies must
already be available:

```sh
cmake -S /tmp/as-resiprocate-m2-20261004 \
  -B /tmp/as-resiprocate-m2-clean-build \
  -DCMAKE_BUILD_TYPE=Release \
  -DUSE_CONTRIB=OFF \
  -DBUILD_PYTHON=OFF \
  -DUSE_MAXMIND_GEOIP=OFF \
  -DBUILD_TFM=OFF \
  -DBUILD_REPRO=OFF \
  -DBUILD_RETURN=OFF \
  -DBUILD_RECON=OFF \
  -DBUILD_REND=OFF \
  -DBUILD_MEDIA=OFF \
  -DBUILD_REFLOW=OFF \
  -DBUILD_TESTING=OFF \
  -DRESIP_HAVE_RADCLI=OFF \
  -DUSE_NETSNMP=OFF \
  -DUSE_GSTREAMER=OFF \

cmake --build /tmp/as-resiprocate-m2-clean-build --parallel 4
```

`build-req.sh` is not the offline handoff path: it may clone from GitHub and
invoke `apt-get`/`sudo` to install dependencies. Prefer the checked-in source
archive and the prebuilt bundle first. If rebuilding requires system packages,
coordinate package installation with the machine owner; do not assume `sudo`
access.

## Python Environment And `uv sync`

The root `uv.lock` is committed and requires `==3.10.*`; `platform/pyproject.toml`
requires `>=3.10,<3.11`. The tested interpreter was CPython 3.10.21. Python
3.9 is not supported by the lock, and Python 3.11+ is outside the platform
constraint.

From the repository root on the receiving machine:

```sh
uv python install 3.10
uv sync --locked --python 3.10
uv run python --version
```

The final command should report Python 3.10.x. In VS Code, select
`${workspaceFolder}/.venv/bin/python`, not a machine-global Python 3.9. The
`--locked` flag checks the committed lock without rewriting it. Package
installation needs access to the configured Python package index or a populated
uv cache/mirror. **`uv sync` does not install CMake/GCC/OpenSSL, does not unpack
the native archives, and does not build reSIProcate.** No Python dependency or
`uv.lock` change was made for this handoff.

## Scope And Risk Decisions To Preserve

1. **M2/M7 boundary is inconsistent across current documents.** `plan.md`
   places TLS transport in M2 and records runtime wiring/REQ-S-1/2/3 as open.
   HLD/LLD describe the product DUM adapter and `CallController` as planned
   integration, while M7 owns production SIP integration. `ADR-0022` is still
   proposed and explicitly says it does not authorize implementation. Before
   implementing the product DUM/Python bridge, have the maintainer decide what
   minimal runnable SIP endpoint belongs to M2 and what full B2BUA control stays
   in M7. Do not treat this uncertainty as evidence that M2 transport work is
   complete.
2. **The local code is a seam, not a stack.** `TlsConfig` checks that mTLS has
   a CA path but does not read files or perform a handshake. `PeerIdentity`'s
   certificate ID is supplied by the future stack binding. `TransportSeam.reload`
   increments a value version but does not install certificates, preserve
   connections, or create an overlap window.
3. **REQ-S-3 is stronger than the smoke.** It requires old and new certificates
   to coexist during a window, current calls to continue, new connections to
   use the new certificate, expired old peers to be rejected or migrated, and
   no process restart. The current smoke replaced one certificate pair and
   observed one active call plus one subsequent connection; it is only
   testbed evidence.
4. **External acceptance is not a coding prerequisite.** Operator-issued PKI
   and a real S-SBC are needed for final end-to-end acceptance, but local CA,
   simulator, and negative-policy tests can drive implementation before that
   access exists.
5. **Keep later gaps separate.** D9 product bridge authorization/design,
   D10/REQ-NF-1 restart recovery, D11 full SDP wire identity, D8 traceability,
   and M6 capacity are separate gates. D8 is a testbed/requirement traceability
   gap; it is unrelated to TLS or certificate rotation, even where older probe
   notes mention both in the same evidence section. Do not silently expand M2
   into the full D10 recovery problem or claim that a native probe closes M7.

## Prioritized M2 Continuation Plan

**P0 — Native SIP stack build and transport smoke.** This is the first
priority. Validate the vendor bundle on the receiving host, add a reproducible
repository build/link path that does not depend on `/tmp` or an implicit
network clone, and run a real `SipStack` listener/client over the selected
transport in a testbed smoke. Keep this P0 to stack/transport construction and
wire exchange; it is not the DUM-to-Python decision path, two-leg B2BUA, or
product `CallController` implementation. Record the supported
OS/compiler/dependency matrix and make the native build reproducible in the
required CI/integration environment.

**P1 — Approve the adapter boundary.** Reconcile `plan.md`, HLD/LLD, and
proposed ADR-0022. Specify whether M2's runnable endpoint is limited to
transport/security or must already invoke Python decisions. Obtain maintainer
authorization before treating the proposed DUM/Python product bridge as an
approved implementation API.

**P2 — Runtime security enforcement.** Wire TLS configuration and fail-closed
peer policy to the actual accepted connection/request path. Test allowed and
denied IP/IP:port and fingerprint peers; verify presented client identity,
certificate chain, and rejection of plaintext. Config changes must be applied
atomically or fail closed; logging must not expose credentials or SIP payloads.

**P3 — Rotation semantics.** Implement the REQ-S-3 dual-certificate overlap
window. Test old and new peers during overlap, active dialog continuity, new
connections selecting the new certificate, expiration/retirement, failed
reload behavior, rollback, and no process restart. Run concurrency/multiple
call tests before claiming acceptance.

**P4 — Acceptance and handoff.** Add focused real-socket integration coverage
and a blocking CI/native-build gate; independently review the implementation;
update requirements, design, plan, and acceptance report. Then obtain
operator-PKI/S-SBC evidence when that environment is available. Keep M6 paused
until the agreed M2 exit criteria are actually met.
