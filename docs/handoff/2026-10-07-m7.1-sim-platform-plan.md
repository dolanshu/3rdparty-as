## 2. 评审问答（2026-10-07）

### REQ-S-2 / REQ-S-3 怎样才算通过

[`test-plan.md`](../acceptance/test-plan.md) §3 的原文是：AS 与 S-SBC 之间的 SIP 走 TLS，明文 5060 被拒绝，并且证书链由**运营商 PKI**签发（S-2）；轮换窗口里正在进行的呼叫不受影响，新连接用新证书，旧证书过期后被拒绝，进程不重启（S-3）。

M7.1 的测试 CA 证明的是传输和轮换机制。按这段原文签 pass，要有运营商 PKI 的签发链。Close 前不做运营商 PKI，所以这两条在 Close 前不能签 pass。若要在 Close 前签过，维护者须改写 test-plan 里「运营商 PKI」这一句，改成接受测试 CA 上的同等行为。M7.1 不改这条口径。

### CPS / SLA 怎样才能发布

对外发布的是维护者写下的 O1 目标，不是某一次 demo 的计数。路径在 [`plan.md`](../plan.md) §5.1 O1 与 §4 的 M6 行：dev-host 实测报告已经有，**目标裁决仍是 open**。裁决写入 CPS、并发会话、建立时延之后，才进入对外口径和 HPA 阈值。AGENT.md §2 禁止的是在这之前把测量值当成承诺。M7.1 结果页可以显示当次运行的发出数和时延，并标明不是容量承诺。

### ADR-0014 的交付物在哪里

ADR-0014 没有一份产品功能清单。它规定 testbed 三层：`contracts/`、`simulators/`、`load/`，并写明 testbed 不随产品交付。客户是否用 testbed 做验收是 [`plan.md`](../plan.md) §5.2 **D6**，仍 pending。本文不把这件事叫作 v1 或 v1.1：`plan.md` §0 已记，仓库没有这两个版本的定义。

产品本身在 plan §4 的 M2–M5（内核、翻译与反诈、控制台、Helm）。testbed 在 plan §2.1 的仓库结构里。`load/` 由 M6 做了。`simulators/` 里的 S-SBC 仿真是 ADR-0003 与 ADR-0014 都写了的，`as_simulators` 包仍是空的。这是测试资产里缺的一层，不是产品范围漏项。M7.1 补的是这一层，仍然不是随产品交给客户的物件。

### REQ-S-4 何时验收

REQ-S-4 验收的是**产品控制台**的授权和审计（test-plan §3：每个写操作校验授权、RBAC、审计不可篡改）。plan §5.4 把正式全绿放在 **M8，或维护者单独签收**。M4b-6a / 6b 的 2026-10-04 签字是工程切片，不是这条 REQ 的验收。矩阵里 REQ-S-4 现在仍是 open。

本次评审：测试工具 UI 可以不登录；产品控制台必须有用户管理。这里的用户管理指产品控制台的登录和基本账号（ADR-0024 的工程切片已在）。plan §5.3 的完整 UM（SSO、MFA、账号全生命周期）仍是未需求化缺口，矩阵为 n-a，本次不扩大产品范围。

模拟平台页面放在 `ims-sim`，不挂产品控制台的 Ingress，也不复用产品登录会话，这样一次 demo 不会被记成 REQ-S-4 已签收。

M8 下一步计划保持搁置。

## 3. 建议拓扑（评审用）

两个 namespace：

| namespace | 里面有什么 |
|---|---|
| `as-sut` | 现有 Helm chart 部署的被测 AS（翻译 / 反诈）、其 Redis 与配置面。沿用已有 chart，不把仿真开关写进生产 values |
| `ims-sim` | 仿真 S-CSCF、仿真 S-SBC、对端 UAS、call load generator、测试 UI |

网络按 ADR-0003 的透明桥接来切：

```text
UI / call load  →  仿真 S-CSCF  →  仿真 S-SBC  →  被测 AS  →  仿真 S-SBC  →  对端 UAS
                   （ims-sim）      （ims-sim）    （as-sut）
```

负载发生器只把 INVITE 送给仿真 S-CSCF。NetworkPolicy 保证它不能直接访问 AS 的 SIP 端口；AS 只接受来自仿真 S-SBC 的 SIP。这样 demo 里的对端才是「模拟的 IMS」，而不是又一个 loopback socket。

仿真 S-SBC 对上游呈现「AS 在网内」，对 AS 呈现「我就是 S-CSCF」，消息按透明桥接转发。这是 POC `src/s_sbc_mock` 已经证明过的行为；实现用本仓库的 reSIProcate 路径，不用 sippy。

TLS 材料只存在于 `ims-sim` 的测试 CA。UI 上固定写明「非运营商 PKI」。

## 4. 呼叫类型与负载

POC 参考（`3rdparty_AS_POC/docs/phase3-plan.md` D7，`tools/call_load_generator.py`）：

| POC 类型 | 行为 | 对本里程碑第一版的建议 |
|---|---|---|
| T1 +86 E.164 → 0 前缀转发 | 翻译接通 | **第一版纳入**，对齐被叫+前缀 |
| T2 0 前缀保持转发 | 翻译接通 | 第一版可纳入，仍是前缀规则 |
| T3 00 → + 转发 | 翻译接通 | 第一版可纳入 |
| T4 短号无匹配 → 404 | 404 | **第一版纳入**（对应 S2） |
| T5 可达下一跳 → 200 | 基本接通 | **第一版纳入**（对应 S1） |
| T6 不可达下一跳超时 | 失败 | 第二期。当前 `as_load` 不做 UDP 重传计时 |
| F1 白名单主叫转发 | 反诈放行 | 第一版纳入，若反诈应用已能在被测 namespace 跑 |
| F2 黑名单 → 608 | 反诈拒绝 | 第一版纳入。产品路径若仍是 603，UI 显示实际响应码，不改写成 608 |
| F3 高频主叫 → 608 | 反诈拒绝 | 第二期。当前产品没有这条规则轴 |
| F4 缺 PAI 失败放行 | 反诈放行 | 第二期。先确认产品是否有这条策略 |

POC 的保持时间模型（约 1 秒接通后保持 2 秒 / 8–15 秒 / 20–30 秒，以及少量不接通）值得借来做**可配置保持时间**。现在的 `as_load` 烟雾是 hold=0，并发数等于累计建立数，不能当多呼叫演示。

第一版负载旋钮：

- 传输：UDP / TCP / TLS
- 启用的呼叫类型（上表「第一版纳入」的子集）
- 目标 CPS
- 持续时间
- 保持时间（或目标并发）。二者至少有一个不是 0

分析页至少给出：发出数、最终响应码分布、接通数、失败数、建立时延、按呼叫类型分桶。SIP ladder 放到第二期。

## 7. 评审结论（2026-10-07）

1. **仿真 S-SBC 是本平台里的一个进程**，跑在 `ims-sim`。它按 ADR-0003 做透明桥：仿真 S-CSCF 发来的 SIP 原样转到被测 AS，AS 的响应原样转回。它不是运营商的设备，也不是今天测试里那个直接把 INVITE 打到 AS 的 UDP socket。负载器只连接仿真 S-CSCF；NetworkPolicy 拒绝负载器直连 AS 的 SIP 端口。
2. **Kamailio 不进第一版。** 已确认。第一种实现就是上面这个透明桥。
3. **模拟平台 chart 与生产 chart 分开。** 已确认。仿真 workload 不进 `deploy/helm` 的默认 values。
4. **环境先用 kind。** 跑通 kind 即本里程碑的环境。
5. **Call load 不做 UDP 重传，也不做 forking。** UDP 重传改由单元测试覆盖。当前 `platform/` 测试里没有 retransmission 用例，M7.1 补上。重传若发生在 reSIProcate 内部，测试放在能看见重发报文的单元或契约层，不放进负载发生器。
6. **不提交 pcap、私钥、测试 CA 的长期密钥。** 测试 CA 在启动时生成，或只用已被仓库忽略的本地材料。
7. **Demo 故事改接本平台**放在 M7.1 完成之后，与文首的 demo 重评是同一件后续，不在本里程碑开工。已确认。
8. **测试工具 UI 不登录。产品控制台必须有用户管理**（登录和基本账号）。完整 UM 的范围见 §2 REQ-S-4 一节。
