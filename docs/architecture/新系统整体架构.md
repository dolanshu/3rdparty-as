## 1. 系统在 IMS 网络中的地位

### 1.1 关键认知修正

第三方 AS **仍然由 S-CSCF 按 iFC 触发**（3GPP TS 24.229）。S-SBC 的引入正是为此，它承担**透明桥接**：

- 对 **S-CSCF 侧**：第三方 AS 被视作**网内 AS**，S-CSCF 无感，消息由 S-CSCF 送出网；
- 对 **AS 侧**：从 S-SBC 来的消息就"是" S-CSCF 来的，AS 也无感、认为自己仍在 IMS 网内。

**架构推论（重要简化）**：AS 只需要实现**一种**接入语义 —— **ISC（被 S-CSCF 触发）**。不需要"网内/网外双模适配器"，trunk 只是承载层而非第二种业务语义。S-SBC 是**运营商侧网元，不属于我方交付物**，但在 testbed 中必须有仿真器。

```mermaid
    style P3 fill:#fdecea,stroke:#ea4335
```

**要点**

- **一进程一用例**：每个用例仍是独立进程/故障域/灰度与扩缩容边界；生产 SIP 方向为 reSIProcate DUM，产品 adapter/controller 尚未实现。
- **无状态化是硬前提，但恢复尚未证明**：已选方向是用 Redis 检查点保存应用层恢复所需的最小呼叫状态，不序列化全部 DUM / `SipStack` 对象（提议中的 ADR-0023）。DUM 运行时仍拥有 live transaction/dialog/session 对象；数据外置不等于能重建这些对象。D10 的 ACK-established-dialog BYE 基线当前仍失败：fresh DUM 的 UAS dialog 返回 481，UAS rehydrate 与产品双腿恢复未解决。REQ-NF-1 保持硬要求；ADR-0002 维持 accepted，措辞与当前 DUM 恢复能力的冲突未解决。
- **亲和性双保险**：LB 层 `sessionAffinity: ClientIP` + 应用层 Redis 会话表兜底（S-SBC 可能复用源端口）。
- **优雅下线**：sippy 阻塞模型下需要 `preStop` draining + 延长 `terminationGracePeriodSeconds`。

### 4.2 单节点容量基线

当前生产栈方向为 reSIProcate（ADR-0019）。单节点 CPS、并发会话与建立时延均未实测；不引用旧候选比较作为容量证据，也不据容量推翻已选栈。容量目标与阈值留待 M6 真实 socket 研究（见 §12.1）。

## 5. 控制面：规则治理与变更流水线

### 5.1 为什么不是 GitOps

运营商网络对 GitHub/GitLab 接入有限制，自建 Git 的成本不在部署而在**运维**：

| 自建方案 | 形态 | 资源 | 结论 |
|---|---|---|---|
| Gitea | Go 单体，单二进制/单容器，内置 SQLite | 1 核 1GB 起（推荐 2 核） | 部署轻，但**只用到 diff/审批一小部分**，且仍要 HA/备份/升级/用户体系 |
| GitLab CE | Nginx + Redis + PG + Sidekiq + Gitaly + Prometheus | **4GB 起，推荐 8GB** | 为一个配置版本库引入分布式系统，**不合算** |

更关键的约束是：**不应要求运营商运维人员为了改号段规则去学 Git/PR**。因此采用 **PostgreSQL + 变更单状态机**。

### 5.2 变更流水线

```mermaid
sequenceDiagram
    participant U as 运维人员
    participant C as console
    participant S as config-service
    participant G as ApprovalGate
    participant R as RuleRepository (PG)
    participant A as AS 实例（多副本）

    U->>C: 编辑规则（草稿）
    C->>S: 提交变更单
    S->>S: schema 校验 + 兼容性检查
    S->>G: 进入审批
    G-->>S: 审批通过
    S->>R: 写入新版本 vN（不可变）
    S->>A: 灰度分发 vN（分批）
    A-->>S: 上报 current_rule_version + 健康状态
    alt 分发/健康异常
        S->>A: 自动回滚至 vN-1
        S->>R: 记录回滚审计
    else 全部健康
        S->>R: 标记 vN 生效
    end
```

**要点**

- 规则仍是**声明式数据**（YAML），业务侧纯函数（`routing/engine`、`screening`）一行不改。
- **每个 AS 实例上报"当前加载的规则版本"** —— 这是 ISSU 期间判断新旧版本规则兼容性的依据（见 §6.2）。
- 接口抽象：`RuleRepository`（版本读写/diff/回滚）与 `ApprovalGate`（审批）。**审批可外置对接客户 OSS/工单系统**，但版本库必须自有 —— 不把规则的可用性绑在客户系统的可用性上。
- 全量操作审计落 PG（承接 §10 安全）。

### 5.3 Feature 开关与能力门控（决策 19）

能力的启停 / 灰度 / 回滚采用**分层门控**，两层各司其职：

| 层 | 粒度 | 生效方式 | 存储 | 与变更流水线关系 |
|---|---|---|---|---|
| ① 部署级总开关 | 整个部署 | 经配置变更流水线**热加载，不重启** | PG 版本库中的一类版本化配置 | 走 变更单 → 审批 → 写 PG → 灰度分发 → 回滚 |
| ② 运行态细粒度覆盖 | 号段 / 呼叫 / 用户 / 百分比 | 热判定（判决时求值） | 状态外置（Redis），最终一致 | 覆盖值同样受流水线治理；判定须幂等 |

**与 §5.2 变更流水线的关系**：feature 开关是流水线中的**一类版本化配置**，与规则走同一条路径 —— 变更单 → 审批 → 写 PG → 灰度分发 → 回滚，不新开通道。

**默认关 + 灰度 + 移除条件（防开关债务）**：

- 每个 feature 必须在 ADR / HLD 显式裁决：是否需要开关、默认态（**默认关**）、灰度策略、**移除条件**。
- 开关只做能力启停，**不改变接口契约**；关闭时走**既有默认路径**。
- 开关是**临时脚手架**，不是永久形态；没有移除条件的开关会在长期维护中持续累积成本。

**机制细节**（两层模型的完整背景、后果与已接受缺口）指向 [ADR-0020](adr/0020-feature-capability-gating.md)。
**运行态覆盖的判定粒度与配置 schema 未定** —— 见 [`../plan.md`](../plan.md) §5.2 未决 **D7**。② 层判决须在 Redis 脑裂窗口下保持幂等（风险 R5、未决 D3）。

## 6. 运营商级三件套

### 6.1 Redundancy

```mermaid

    subgraph SITE_A["主站点 · 承载流量"]

        A1["AS 副本组<br/>N+1"]

        A3["console<br/>多副本"]

    end

    subgraph SITE_B["备站点 · 温备（常驻不接流量）"]
        direction TB
        B1["AS 副本组<br/>容量 ≥ 主站"]
        B2["config-service"]
        B3[("Redis")]
        B4[("PostgreSQL")]
    end

    A5 -. "规则/审计同步" .-> B4
    SCSCF3["S-CSCF / S-SBC<br/>trunk 优先级路由"] ==>|"主用"| SITE_A
    SCSCF3 -.->|"故障切换"| SITE_B

    style SITE_A fill:#e6f4ea,stroke:#34a853
    style SITE_B fill:#fef7e0,stroke:#f9ab00
```

**站点内：零单点**（N+1，容忍单节点故障）
- AS 无状态多副本；config-service / console / 可观测汇聚多副本；
- **交付落点（[ADR-0026](adr/0026-in-cluster-state-stores-proposal.md)）**：治理 PG 与运行 Redis 与 AS 工作负载在**同一客户 namespace** 内由 Helm `stateStores` 渲染（或客户托管 endpoint）；**不是**运营商 IMS 核心库。
- Redis 升 Sentinel（**D3 / M2**）；PG 流复制 + 定期备份 + PITR；
- 有状态组件（Redis、PG）均纳入冗余与备份清单（实施见 `docs/acceptance/m5-state-stores-runbook.md`）。

**跨站点：1+1 温备**
- 备站常驻但不接流量，规则/配置经 config-service 同步；
- 切换靠 S-SBC 侧 trunk 优先级 + 自动/手动脚本；
- **不采用双活（active-active）**：流量如何两站点分担由运营商网元配置决定，不在我方控制范围；且双活要么跨站点共享会话状态（延迟 + 脑裂），要么接受故障瞬间在途呼叫丢失 —— 这个 SLA 应由运营商定义。温备的切换语义最简单：备站无在途呼叫。

> ⚠️ 若要求容忍**整个机架/AZ** 故障（N+M），Redis 需跨 AZ、Pod 强制打散 —— 当前按 N+1（单节点）记，需变更请指出。

### 6.2 In-Service Upgrade（ISSU）

**前提事实**：`sippy==2.4.2` 是阻塞 `ED2.loop()`，SIP 事务/对话状态**全在进程内存**、无序列化与迁移接口 —— 因此"把在途呼叫无缝移交给新版本"在架构上**不成立**。ISSU 只能走 **draining**。

```mermaid
stateDiagram-v2
    [*] --> Serving: 新版本副本就绪
    Serving --> Draining: 摘流（readiness 失败 → 退出 Endpoint）
    Draining --> Draining: 存量呼叫继续处理<br/>不再接新呼叫
    Draining --> Exited: active_calls == 0
    Draining --> ForceRelease: 超过 grace window
    ForceRelease --> Exited
    Exited --> [*]
```

**规则与约束**

| 项 | 约束 |
|---|---|
| 升级窗口 | ≈ 存量呼叫最长时长，grace window 可配；需定义"超时强制释放"策略与呼叫时长硬顶 |
| 版本共存 | 新旧版本并存期间**规则 schema 必须双向兼容** —— 因此"规则 schema 版本化 + 兼容矩阵"是 ISSU 的硬前置 |
| 证书轮换 | 视同一次配置热更新，**不得触发重启**、不得中断在途呼叫 |
| 编排 | k8s RollingUpdate + `preStop` draining + 延长 `terminationGracePeriodSeconds` + PDB |
| v1 不做 | Operator（Helm + 标准 Deployment/ConfigMap/Secret 足够） |

### 6.3 动态扩缩容（grown / down-grown）

```mermaid
flowchart LR
    M["指标<br/>active_calls · cps · CPU"] --> HPA{"HPA / 自定义指标"}
    HPA -->|"超阈值"| UP["扩容<br/>新副本：启动 → 拉规则 → 就绪"]
    HPA -->|"低于阈值"| SEL["缩容保护控制器<br/>挑 active_calls 最少的 Pod"]
    SEL --> DRAIN["标记 draining annotation"]
    DRAIN --> Q{"active_calls == 0 ?"}
    Q -->|"否"| WAIT["继续等待"]
    WAIT --> Q
    Q -->|"是"| DEL["删除 Pod"]
    PLAN["容量规划<br/>话务模型 → minReplicas"] --> HPA

    style SEL fill:#fdecea,stroke:#ea4335
    style Q fill:#fdecea,stroke:#ea4335
```

**要点**

- **不用标准 CPU/内存 HPA**：sippy 是阻塞事件循环，CPU 与真实 SIP 负载相关性差；更致命的是它**看不见活跃会话**，缩容必然掉话。
- **缩容保护控制器是必需品，不是优化项**：先摘流 → draining → `active_calls==0` 才删除。原生 controller 挑 Pod 策略不可控（类似 cluster-autoscaler 的 safe-to-evict 思路）。
- **新增两个指标**：`active_calls`（gauge）、`cps`（rate）。现有 `MetricsRegistry` 只有 `CallDisposition`/`PeerStatus`，需扩展；这两个指标同时服务于 OTel 与扩缩容。
- **扩容时延**：新副本要启动 + 从 config-service 拉规则才能接呼叫 → 潮汐预扩（D 方案）留 **v1.1**，v1 只做 A。
- 配置基线 `minReplicas` 按话务模型设定，HPA 只做**突发兜底**（节假日、群呼、以及反诈场景下针对本系统的呼叫洪峰）。

## 7. 数据面

| 存储 | 承载 | 冗余要求 | 说明 |
|---|---|---|---|
| **Redis** | 呼叫 signaling/controller 必要状态 checkpoint 方向、独立 rate-window aggregate state、信誉衰减 | Sentinel（1 主 2 从 3 哨兵） | `StateStore` + `InMemoryStateStore` / `RedisStateStore` 是通用存储 seam；不等于已有呼叫 recovery adapter |
| **PostgreSQL** | 规则版本、变更单、审计流水、控制台用户/权限 | 流复制 + 备份 + PITR | 数据量极小（规则条目千级、审计慢增长） |
| **呼叫轨迹** | 按 Call-ID 的逐消息记录 | 短期持久化（保留期可配） | 运维/举证数据，**非话单** |

**呼叫 checkpoint 与聚合运行态分开。** Redis 应用层呼叫 checkpoint 是提议中的 ADR-0023 方向，拟保存一通呼叫两条 leg 与 controller 恢复所需的完整逻辑单元；目前尚无 recovery adapter 或 D10 通过证据。rate-window counter 是独立的 aggregate domain，不逐通复制进 dialog checkpoint。当前 anti-fraud 决策函数只接收调用方注入的只读 counters；app 源码/测试中尚无 `StateStore` 写入接线。translation 决策模块没有 app-specific per-call state。PostgreSQL 仍只承载 governance data，不是本次选定的呼叫 checkpoint。

**明确不做**：CDR 采集、CDR 投递通道、CDR 归档存储 —— 网外不计费（修正 2）。

**Redis 脑裂兜底**：Sentinel 切换窗口内，反诈速率窗口可能重复计数 → 判决需在极端情况下保持幂可接受，风险见 §12。

```mermaid

    subgraph APP["AS / config-service / console"]

    SIG1 -->|"OTLP"| COLL["OTel Collector"]
```

**双重身份必须拆开**：呼叫轨迹既是**运维信号**（走 OTel trace 进 Tempo/Jaeger），又是**产品能力**（控制台按 Call-ID 查询、投诉追溯、反诈举证）。后者**不能依赖客户是否部署了 trace 后端**，因此保留 AS 自身的 `/api/v1/traces` 查询通道，两条通道用同一 **Call-ID / TraceID** 关联。

1. **导出不能阻塞呼叫路径**：sippy 阻塞 `ED2.loop()`，OTel 批量导出必须走独立线程/后台 flusher，否则可观测性会变成 SLA 杀手。
2. **进程内内存指标在多副本下无意义**：现状 `MetricsRegistry` 是进程内内存视图，必须改成每 Pod 暴露 endpoint + 集中抓取聚合。

**告警**：POC 没有告警，v1 补上；规则集随产品提供，不绑定后端。

## 10. SIP 栈与产品 B2BUA 控制

生产 SIP 栈仍为 **reSIProcate C++**（ADR-0019）；旧版候选比较与迁移路径材料不再描述当前方向。sippy 仅作为 `testbed/` 行为基线参考。DUM 提供 SIP session、dialog、transaction 机制，不等同于完整产品 B2BUA。

产品逻辑 `CallController` 位于 DUM 之上：关联独立的入站 UAS 腿和出站 UAC 腿及其不同 Call-ID；把 DUM session 事件转成业务决策和出站命令；协调 provisional/final response、CANCEL/BYE、in-dialog 请求、非 2xx、竞态与清理；并调用既有 Python 决策模块。事务重传和协议定时器由 DUM 所有，不能在 controller 中重复实现；DUM 回调必须非阻塞。详见[提议中的 ADR-0022](adr/0022-resiprocate-b2bua-control.md)、[HLD](hld.md) 与 [LLD](lld.md)。

集成设计尚未确定：上游 1.14.0 的 `BUILD_PYTHON=ON` 不提供通用 `resip`/DUM Python 模块。原生 C++ DUM S1/S4 自环 smoke 不是产品 E1，也不是需求验收。实现产品适配器前必须完成 Python/native 集成 spike；同时必须证明进程重启后的协议/dialog 状态恢复满足 REQ-NF-1/E5，或形成明确设计缺口评审。DUM 运行中的协议对象不等于可序列化至 Redis 的对象；REQ-NF-1 保持硬验收要求。ADR-0019 的栈选择不变，K2 和 E1/E4/E5 仍开放。

**Feature 门控**：
